# Как это работает

## 1. Части системы

```
сборка игры ──► Launcher.Publish ──► out/site ──SFTP (WinSCP)──► хостинг (статика)
                                                                  │
лаунчер у тестера ◄──────────── HTTPS GET ────────────────────────┘
```

- **`Launcher.Core`** — вся логика. UI и утилита публикации — тонкие оболочки над ним.
- **`Launcher.Publish`** — строит раскладку сайта из папки сборки.
- **`tools/publish.ps1`** — вызывает `Launcher.Publish` и синхронизирует раскладку с хостингом.
- **`Launcher.App`** (WPF, .NET Framework 4.8) и **установщик** (Inno Setup) — следующие этапы.

## 2. Раскладка на сервере

```
<корень>/
  manifest.json
  objects/ab/ab12…ef.gz          файл сборки, сжатый gzip, имя — SHA-256 несжатого содержимого
  media/0.0.11-screenshot.png
  media/0.0.11-changelog.md
  launcher/FloxLauncher-1.0.2.exe
```

Объекты неизменяемы: одинаковое содержимое лежит один раз, под своим хэшем, и никогда не
перезаписывается. Отсюда два свойства:

- **Атомарность релиза.** Публикация сначала заливает новые объекты, `manifest.json` — последним.
  Пока он не заменён, лаунчеры видят старую версию целиком; после — новую целиком. Полузалитого
  состояния не бывает.
- **Сжатие без настройки хостинга.** gzip применён к самим файлам, лаунчер распаковывает сам;
  `Content-Encoding` от сервера не нужен.

Почему так — [ADR-0001](adr/0001-content-addressed-static-release.md).

## 3. Манифест

```json
{
  "game": {
    "version": "0.0.11",
    "minVersion": "0.0.11",
    "exe": "PotteryBraker.exe",
    "files": [
      { "path": "PotteryBraker_Data/data.unity3d", "size": 1234, "packedSize": 567, "sha256": "…" }
    ]
  },
  "launcher": { "version": "1.0.2", "url": "launcher/FloxLauncher-1.0.2.exe", "size": 1, "sha256": "…" },
  "screenshot": "media/0.0.11-screenshot.png",
  "changelog": "media/0.0.11-changelog.md"
}
```

- `path` — относительный путь с `/`. `ManifestValidator` отвергает `..`, `.`, пустые сегменты,
  обратный слэш, `:` и ведущий `/` — манифест не может заставить лаунчер писать за пределы папки игры.
- `size` — размер файла, `packedSize` — размер объекта на сервере (по нему считается прогресс).
- Файлы с `DoNotShip`/`DontShip` в любом сегменте пути (папки Burst и IL2CPP-бэкапа Unity) в релиз не
  попадают.
- Версии сравниваются как `System.Version` по части до `-`/`+` (`0.0.9 < 0.0.10`); пустая версия
  старше любой.
- Лаунчер запрашивает `manifest.json?t=<ticks>`, чтобы обойти кэш хостинга.

## 4. Раскладка на машине тестера

`InstallLayout` над корнем `%LOCALAPPDATA%\FloxStudios\<Игра>\` (права администратора не нужны):

```
game\             файлы игры
staging\          скачанные и проверенные объекты текущего обновления
installed.json    версия, exe и кэш хэшей установленных файлов
```

Сейвы Unity живут в `%USERPROFILE%\AppData\LocalLow`, поэтому удаление лишних файлов из `game\`
их не задевает.

## 5. Обновление

`GameUpdater.Plan` → `GameUpdater.ApplyAsync`:

1. **Скан.** `LocalScanner` обходит `game\`. Если размер и `LastWriteTimeUtc` файла совпадают с
   записью в `installed.json`, хэш берётся из кэша, иначе файл хэшируется заново.
2. **План.** `UpdatePlanner` сравнивает скан с манифестом: какие объекты скачать (уникальные по
   хэшу), какие файлы положить, какие удалить, какие не трогать.
3. **Загрузка.** До четырёх объектов параллельно, каждый — в `staging\<sha>.part`, распаковкой на
   лету. После записи файл хэшируется; несовпадение удаляет его и бросает `InvalidDataException`.
   Проверенный объект переименовывается в `staging\<sha>` — при повторном запуске после обрыва
   он не качается заново.
4. **Установка.** `installed.json` удаляется, файлы копируются из `staging\` через
   `<файл>.incoming` → замена, лишние файлы и опустевшие папки удаляются, `installed.json`
   пишется заново (через `.tmp` → замена), `staging\` удаляется.

Гарантии при обрыве:

- Обрыв на шаге 3 не трогает установку: старая версия остаётся рабочей и запускаемой.
- Обрыв на шаге 4 оставляет установку без `installed.json` — лаунчер считает игру неустановленной
  и не даст её запустить, пока обновление не пройдёт до конца. Повтор досканирует изменённые
  файлы, докачает недостающее и доведёт установку до манифеста. Хвосты `.incoming` окажутся
  «лишними» файлами и будут удалены.

Обновление требует, чтобы игра не была запущена: иначе Windows не даст заменить её файлы.

## 6. Политика запуска

`LaunchPolicy.Decide(installedVersion, manifest)`:

| Состояние | Когда | Играть | Обновить |
|---|---|---|---|
| `NotInstalled` | сервер доступен, игры нет | — | да |
| `UpToDate` | установлено ≥ `version` | да | — |
| `UpdateAvailable` | `minVersion` ≤ установлено < `version` | да | да |
| `UpdateRequired` | установлено < `minVersion` | — | да |
| `OfflineInstalled` | сервер недоступен, игра есть | да | — |
| `OfflineNotInstalled` | сервер недоступен, игры нет | — | — |

`Launcher.Publish` по умолчанию ставит `minVersion = version`, то есть каждое обновление
обязательное. `--min-version` оставляет старые версии разрешёнными. Без сети лаунчер пускает в уже
установленную версию — [ADR-0004](adr/0004-mandatory-update-but-offline-play-allowed.md).

## 7. Самообновление

Если `manifest.launcher.version` новее собственной версии лаунчера:

1. `SelfUpdater.DownloadAsync` качает exe в `<exe>.new` и проверяет SHA-256.
2. `SelfUpdater.Swap` переименовывает запущенный `<exe>` в `<exe>.old` (Windows разрешает
   переименовать исполняемый файл запущенного процесса), кладёт `.new` на его место; при ошибке
   откатывает переименование.
3. Лаунчер перезапускает себя и выходит; новый процесс на старте вызывает
   `SelfUpdater.CleanupPrevious`, удаляющий `.old`.

Почему не bat-скрипт и не отдельный updater — [ADR-0003](adr/0003-self-update-by-renaming-running-exe.md).

## 8. Публикация

```powershell
./tools/publish.ps1 -BuildDir <папка сборки> -Version 0.0.11 -Exe PotteryBraker.exe `
    [-MinVersion 0.0.10] [-Screenshot shot.png] [-Changelog changelog.md] `
    [-LauncherExe FloxLauncher.exe -LauncherVersion 1.0.2] [-SiteDir out/site] [-NoUpload]
```

1. `Launcher.Publish` хэширует файлы сборки, сжимает в `out/site/objects/` только новые объекты,
   копирует медиа и exe лаунчера, пишет `manifest.json`.
2. WinSCP синхронизирует `out/site` с сервером **без** `manifest.json` (сравнение по размеру —
   объекты неизменяемы, так что уже залитые не передаются повторно), затем отдельно заливает
   `manifest.json`.

`out/site` — локальное зеркало сервера, его не удаляют между публикациями: по нему видно, какие
объекты уже есть.

Доступ — переменные окружения (в репозиторий не попадают):

| Переменная | Что |
|---|---|
| `LAUNCHER_SFTP_HOST` | хост |
| `LAUNCHER_SFTP_USER` | пользователь |
| `LAUNCHER_SFTP_PASSWORD` | пароль (или `LAUNCHER_SFTP_KEY` — путь к `.ppk`) |
| `LAUNCHER_SFTP_HOSTKEY` | отпечаток ключа сервера, `ssh-ed25519 255 …` (WinSCP показывает при первом входе) |
| `LAUNCHER_SFTP_DIR` | папка на сервере, из которой раздаётся сайт; должна существовать |

## 9. Не сделано

- Чистка старых объектов на сервере: сегодня `objects/` только растёт.
- Подпись exe: неподписанные `setup.exe` и лаунчер вызывают предупреждение SmartScreen.
