# ADR-0001: Релиз — статика с объектами по SHA-256 и манифестом, заливаемым последним

- **Статус**: принято
- **Дата**: 2026-09-10

## Контекст

Сборки раздаются с обычного хостинга: только статика и доступ по SFTP, никакого серверного кода.
Сборка Unity — сотни мегабайт, но от версии к версии меняется малая часть файлов. Тестеры
обновляются часто, и заливка идёт с домашнего канала.

## Решение

Каждый файл сборки хранится на сервере как `objects/<первые 2 символа>/<sha256>.gz`, где хэш — от
несжатого содержимого. `manifest.json` перечисляет пути, размеры и хэши. Публикация заливает
недостающие объекты, затем манифест. Лаунчер качает только объекты, которых нет среди его файлов,
и проверяет каждый по хэшу.

## Рассмотренные альтернативы

**Один zip на версию.** Проще всего и в публикации, и в лаунчере. Отвергнуто: каждое обновление —
вся сборка целиком и для тестера, и для заливки; обрыв загрузки начинает всё заново.

**Бинарные дельты (bsdiff/xdelta) между версиями.** Меньше всего трафика. Отвергнуто: нужны
цепочки патчей между каждой парой версий или обязательное прохождение всех промежуточных, а Unity
перепаковывает `.assets`/`.resource` так, что выигрыш над пофайловой схемой непредсказуем.
Можно добавить позже поверх той же схемы.

**Файлы по их путям вместо хэшей (`files/<версия>/<путь>`).** Нагляднее на сервере. Отвергнуто:
одинаковые файлы разных версий хранятся и заливаются заново, а замена файлов по тому же пути ломает
тестеров, скачивающих в момент заливки.

**itch.io + butler.** Уже есть аккаунт, butler умеет дельты. Отвергнуто при выборе хостинга: для
закрытой раздачи без логина и со своим окном нужен собственный сервер.

## Последствия

- Объекты неизменяемы, релиз атомарен относительно замены одного небольшого файла.
- Хостинг не должен уметь ничего, кроме раздачи файлов по HTTPS.
- `objects/` только растёт; чистка неиспользуемых объектов — отдельная задача.
- Локальное зеркало `out/site` у публикующего — источник знания о том, что уже залито.
